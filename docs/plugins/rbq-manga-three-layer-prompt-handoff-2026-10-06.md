# 漫画提示词三层分工：实施交接方案

日期：2026-10-06。

本文件保留交接设计，并记录已完成的首版实施。当前代码版本为漫画 **1.9.33** / SDT **6.5.22**；下方实施记录区分已验证的工程行为与尚未验证的模型、成图效果。

设计核对基线：Git `eb728d6`，漫画插件 `1.9.32`，SDT `6.5.21`。后续接手前仍需重新检查实际 HEAD、工作区与插件版本，不覆盖用户或其他模型的新改动。第 3 节描述该基线的冲突，不是本次实施后的新路径。

## 实施记录（2026-10-06）

首版已按 A～C 接通，D 的工程验收和文档已完成，可作为独立试用选项使用；真实模型与成图对照尚未执行。新增 ID 为 `v_manga_layered_v1`，旧选择和默认值不迁移。

三个公共模块固定为 `manga_contract_v1`、`manga_story_v1`、`v23_manga_v1`。`mangaProtocol.resolvePromptPreset(ec)` 解析组合；`buildPromptBundle({presetDescriptor, task, settingsSnapshot, canvas, referenceOptions, responseKind, transport, limits})` 返回 `instructionText/schema/outputExample/trace`；`validatePromptResult(data, trace)` 在缓存、档案和草稿写入前检查任务范围，不修改响应。构建器不读全局设置、发请求或写档案。

| 实际入口 | task / responseKind | 已执行的范围 |
| --- | --- | --- |
| SDT 正文 JSON / tool / custom | `adapt_message` / `story` | 当前正文改编，可多页；无内容时可 `shouldDraw=false` 且空 segments |
| SDT 手动描述 | `adapt_manual` / `story` | 明确绘图任务，可多页，必须返回至少一页 |
| SDT 测试 | `test_page` / `story` | 严格一页，不截取多页响应 |
| SDT 已有页修改 | `refine_page` / `page` | 编辑完整页快照，不接收 segments 包装，不重新选材 |
| Studio 新分镜 | `studio_page` / `studio-page` | 单页自动 1～5 格或指定格数，经典四格严格四格 |
| Studio 单格修改 | `refine_panel` / `studio-page` | 返回当前一格，其他格只作连续性参考 |
| Studio 批量修改 | `refine_panels` / `studio-page` | 保留现有格数与次序，现有竞争请求保护继续生效 |

新组合的真实请求不再混入旧 `segmentInstruction/contextAnalysisInstructions/manualInstruction`。参考资料保留原入口的开关；风格预设在原支持注入的 SDT 入口以用户资料发送，Studio/已有页润色不新增注入。快照覆盖组合、系统/工具组装、画布、对白、画风及相关设置；成功结果的 trace 保留模块版本和任务，不进入 NAI 绘图文字。

新增 [分层专项测试](../../test/run-manga-layered-prompt-tests.js) 共 36 项，覆盖各入口的实际请求、两种对白、模型响应到 NAI 字幕的编译闭环、范围校验、缺页布局、工作台拟音开关、工具降级与等待期间设置切换。任务范围错误有独立诊断指引，不误报缺页或拒答。四份历史规划 hash 和旧主链路两种对白 × 三种传输的实际请求指纹保持；其余 Studio、记忆、灰阶、气泡与生命周期回归一并通过。全部 `run-manga*tests.js` / `run-sdt*tests.js` 为 **34 个脚本、784 项通过**；语法、版本/URL 与 `git diff --check` 通过。

验证使用中性办公/递信剧情和模拟接口，没有真实模型/生图调用。三个模块在同一次请求中分工，没有程序冻结中间计划；提示是否可靠覆盖正文、严格保持每格事实，以及模型是否能画准气泡，仍需第 14 节的实际对照。可用配置与使用步骤见 [漫画使用说明](rbq-manga-mode.md)。

## 1. 最终推荐

采用 **三个职责模块、一次模型请求、一份现有漫画 JSON**：

1. **漫画基础规范**：规定漫画的表达方式与数据合同。
2. **正文漫画规划**：决定当前正文画什么、分几页、各页几格、怎样切分及每格内容。
3. **V23 格内绘图指导（漫画适配）**：把已经确定的画面写成准确的绘图标签。

另外把角色资料、前文、画布、风格预设作为输入资料；它们不再各自携带一套分页或输出指令。

首版新增一个明确分层的规划选项，使用独立 ID，例如 `v_manga_layered_v1`。内部绑定经过人工整理的 `v23_manga_v1` 格内模块，不要求用户同时到普通 SDT 系统预设中再选一次 V23。已有规划保持历史兼容。先提供可选择的新模式，通过实测后再考虑调整新安装的默认值。

这一轮优先解决 SDT 正文解析，随后接通其余漫画入口和工作台的现有单页任务。保留现有编译、气泡归属、说话者引用、角色记忆及绘图快照机制。

## 2. 必须统一的术语

- “正文生成漫画”是改编已存在的 `currentMessage`，不是让漫画解析器续写故事。
- 漫画模式中的“前情增强”实际上负责正文改编规划。建议界面在漫画模式下显示为“正文漫画规划”，普通插画模式仍保留原名称。
- “与原版一样”指保留原版漫画表达和绘图协议的能力，不是原样复制整份旧提示词。当前已经支持结构化气泡、灰阶缓存、角色状态；不能为了复刻原文而倒退这些能力。
- SDT 内置 `v23` 系统预设与“提示词预设”插件中的用户预设不是同一个对象。不能仅凭预设名称含 V23 就认定它是本方案的格内模块。
- 一张最终漫画图是一页；一个 `segment` 是一页；`panels` 是页内画格；`characters` 是各格的人物出场。同人跨格出场不能混同为多个身份。

## 3. 已核实的现状与冲突

以下按函数定位，行号随实施变化，不应机械套用。

| 当前位置 | 实际行为 | 问题 |
| --- | --- | --- |
| `manga-mode.js / buildMangaSystemPrompt` | 同时写分页、布局、人物资料、V23 动作、气泡、灰阶、输出规则 | 基础合同与规划、格内生成混合 |
| `MANGA_PLANNING_PROMPTS.v_manga_v5` | 同时包含页面布局与动作生成等要求 | 与共享系统提示重复，无法独立更换格内指导 |
| `getEnhancedContextPayload`、`getEnhancedContextSystemPrompt`、`segmentInstruction` | 以摘要、系统段落、任务文本再次传递部分规划要求 | 多处维护，容易出现覆盖范围或单页/多页规则不一致 |
| `getSystemPromptWithPresets` | 漫画请求改用 `mangaProtocol.systemPrompt`，绕过普通系统预设 | 普通 SDT 选中的 V23 并不自动成为漫画第三层 |
| `injectPresetsToTagger` 分支 | 把外部预设的正负词作为风格说明追加到系统提示，也放入 `stylePreset` | 风格资料与指令混合，说明还使用普通 `scene` 字段语义 |
| `prompt-presets.js / buildNaiV4Payload` 钩子 | 正负预设、前后缀直接拼入整页基础绘图词 | 不是逐格绘图指导；整份系统指令放进去会直接污染生图词 |
| `studioDirectorPrompt`、SDT 已有页润色 | 各自拼接任务与输出要求 | 易遗漏公共规则，也可能把全文分页要求带进单格修改 |

外部预设当前只把 `positive/negative` 送给 Tagger；最终绘图钩子还会处理 `positiveSuffix` 和全局前后缀等字段。因此“模型参考到的风格”和“最终送图的全部预设”目前也不是同一份数据。首版先准确展示与记录，不顺手扩大注入范围或改写用户预设。

四个历史规划 `v_manga`、`v_manga_185`、`v_manga_161`、`v_manga_150` 的文本有长度与 SHA-256 回归。保留这些历史文本不能仅靠修改测试预期来达成。当前还有 `v_manga_narrative`、`v_manga_v5`，其已存选择同样不能被自动改名或迁移。

## 4. 三层职责与决策归属

| 决策 | 唯一负责层 | 其他层如何使用 |
| --- | --- | --- |
| 字段、类型、ID、页格人物嵌套、输出格式 | 基础规范 | 按合同输出，不另发明格式 |
| 原色资料、临时状态、灰阶视图及缓存语义 | 基础规范 | 规划识别正文变化，格内模块按规则表达 |
| 字幕存在哪一层、`speaker_id`、画外声明 | 基础规范 | 规划判断实际发言人及可见性，再填正确字段 |
| 是否值得画、选哪些正文内容 | 正文规划 | 格内模块不得重新筛选 |
| 页数、页界、每页任务、格数、格位、面积、阅读路径 | 正文规划 | 格内模块把已定版式写进实际绘图字段 |
| 当前格定格时刻、出镜人物、镜头、对白及顺序 | 正文规划 | 格内模块实现具体姿态与视觉细节 |
| 如何表达左右手、接触点、视线、表情、环境、局部负词 | 格内指导 | 不改变事件、镜头任务、人物和文字 |
| 字面画风、材质、色调参考 | 独立风格资料 | 在既定画风/黑白约束内影响视觉词 |
| 一页/一格编辑边界、固定格数、取消和过期响应 | 调用器与程序校验 | 任何提示模块不得越权 |

明确边界：基础规范可以要求“格数必须与 `panels.length` 一致”，不负责决定“这段正文必须三格”；可以规定阅读方向，但实际横排/纵排、大小与邻接由规划层安排。

用户当前任务和正文事实约束整个过程；格式与引用合同保证输出可用；规划偏好只在没有明确限制时起作用。不要把某一种文法的偏好升格为所有题材的硬条件。

## 5. 基础规范如何整理

新增独立构建函数，例如 `buildMangaContractPrompt(snapshot)`。从现有系统提示中人工提取以下内容，保持语义：

- 每个 segment 对应一页，页/格/人物结构及阅读顺序的表达规则。
- 同人跨格 ID、稳定身份、完整 base/outfit、临时 state 与历史快照规则。
- 灰阶 render 的来源、复用和缓存，不反写原色角色档案。
- 结构化与旧格式两种对白分支；同一次请求只启用所选的一种。
- 气泡文字归属、已支持的 `speaker_id` 归位条件、显式画外语义和空数组清空。
- 自动/手动定位条件、整页坐标含义及合法输出要求。
- 所有应当生效的版式/动作信息必须进入绘图字段，不能只写在 `reason/intent`。

从新基础模块移出：页数推导、黄金主格比例、景别轮换、固定事件链、V23 动作流水线、权重矩阵、按正文择镜的策略。文法和边框选项仍是输入；由规划层决定应用在哪里，基础层只保留必要的表达限制。

基础模块包含一份简洁的完整中性嵌套例子，展示页/格/人物/气泡关系。例子以 Schema 为依据维护，明确只示范字段关系，不暗示所有输出都用相同页数、格数、人物数或布局。

## 6. 正文规划如何工作

新规划模块的推导顺序：

1. 通读当前正文，确定已发生的事件、问答、信息变化及直接反应；前文仅补身份和连续状态。
2. 选择漫画需要呈现的关键内容，保留因果与结尾。去掉纯重复描述，不把每个句子机械变成一格，也不只取最后一个高潮。
3. 拟定页面任务和内容边界。事件、对白、场景转换共同决定页数；不先按字数或模板锁死页数。
4. 每格选一个可同时成立的定格时刻，写清出镜者、主动作、接触对象、必要环境、对白及发言人。先后发生、互斥的动作分格处理。
5. 按理解画面所需选择景别、机位、人物关系与文字空间。允许连续相同机位、均衡分格、无字格和单格页。
6. 依据真实画布宽高、朝向和每格画面/文字负荷，调整格数、页界和大小。文字太多时优先重新分配与分页，不切掉关键回答或结尾。
7. 明确每页各排/列的切分、相邻关系、相对大小与阅读路径；保证页级描述、格级位置和人物位置一致。
8. 输出最终页树及简短 `reason/intent`。不要求输出长推理、独立事件账本或两套重复的完整计划。

所选台词属于哪位人物、在这一格是画内还是画外，是规划层的语义判断；基础层规定其表示方法，格内层不得为便于排版而改说话者、改文字或伪装成画外声。

“主格较大”“插入特写”“某处留白”应有正文和表现目的依据。固定比例、每页必须高潮、每页必须悬念、禁止等分等不能成为新通用规划的默认硬规则。用户明确选择特定排版任务时，按该任务执行。

首版继续使用 `intent` 和现有绘图字段，不新增必填 `story_plan/beat_ids/source_ledger`。锚点仍按当前合同逐字摘录正文；页的实际覆盖不能仅凭一个短锚点证明，需要评估整页内容。

## 7. V23 怎样提取才适合漫画

新增 `MANGA_PANEL_PROMPTS.v23_manga_v1`，保存经过人工整理的独立模块。不要运行时用正则截取整份普通 V23，也不要改写普通 SDT 的 `CONSISTENT_SYSTEM_PROMPT_V23`。

| V23 内容 | 漫画适配方式 |
| --- | --- |
| 朝向→位置→基础姿势→肢体动作→行为→表情→视线→状态 | 保留为描述检查顺序；实际标签排序兼顾重要性，不强求每格填满全部项目 |
| 左右手各自任务、道具和接触关系 | 保留；只有正文及定格时刻支持时才写，区分伸手接近与已经握住 |
| 复杂动作拆成明确、相容的视觉描述 | 保留，避免抽象概括和互斥姿势堆叠 |
| 重要性排序、相邻关联词、权重语法 | 复用当前编译器支持的语法，权重克制；效果需实测，不承诺权重能修复错人或缺失信息 |
| 状态、表情和即时反馈 | 以当前正文和已知状态为依据，不自动递增权重、不自行添加状态变化 |
| 镜头与人物动作区分 | 镜头/环境写格级，人物动作写本人 `positive`；落实规划选定镜头，不随机轮换 |
| 普通 `scene/action/uc` 等输出合同 | 移除，适配成现有 `page/panels/characters` 字段 |
| 重新判断 `shouldDraw`、决定 segment 数量 | 移除，这属于规划层 |
| 自动猜国籍、年龄或填满外貌维度 | 移除，身份依据统一由基础规范和角色资料管理 |
| 固定人数决定景别、强制镜头轮换、机械累积状态 | 不作为通用硬规则，按实际画面处理 |
| 交互前缀或特殊写法 | 只有当前目标模型/编译链已支持时才保留，不因原文出现就承诺有效 |
| 固定坐标和人物重叠模板 | 不继承，位置以已定格布局及定位模式为准 |

字段映射：

- `page.base`：把规划给出的整页形态、实际格数、布局、共用光照写成绘图描述，不能借此重排页面。
- `panel.description`：该格位置、大小、所选景别/机位、环境与空间关系。
- `panel.non_character`：非人物视觉信息；文字表达仍服从当前对白模式。
- `character.positive`：这一格中的位置、姿态、肢体、对象、表情和视线。
- `character.negative`：有依据、当前镜头适用的具体互斥误画因素；可以在本人的负词中排除容易串入的其他人物独有特征，但不能排除本人正确特征或双方共享特征，不能把他人应有的特征写入整页全局负词，也不能排除必要漫画元素。
- `base/outfit/state/render`：沿用基础规范的资料和变化语义，不以景别为由清空完整档案；可见性由本格演出与景别表达。
- `bubbles`：保留规划分配的文字、归属与顺序，按基础协议输出；第三层不润色台词。

示例任务为“甲伸手递信，乙尚未接住”。可以写甲握信、乙伸手接近、视线朝信件；不能写成双方已握住或乙已收进抽屉。是否再画接信完成，由规划决定。

## 8. 统一提示组装与请求快照

在 `mangaProtocol` 新增纯构建接口，例如：

```js
buildPromptBundle({
  presetDescriptor,       // 已解析且冻结的组合 ID 与模块版本
  task,                   // 整段改编、单页生成、已有页修改、单格修改
  settingsSnapshot,       // 画风、语言、文法、边框、对白模式、定位方式
  canvas,
  referenceOptions,      // 是否使用角色卡/记忆/风格，均为请求快照
  responseKind,           // story、page、studio-page 等现有入口形状
  transport              // json 或 tool：只影响交付要求
})
// -> { instructionText, schema, outputExample, trace }
```

以上是目标接口示意，不代表这些函数或字段已经存在。实现时按现有工具链最小调整。

组合描述表至少包含：`assemblyVersion`、`contractModule`、`plannerModule`、`panelModule`。`enhancedContext` 继续作为规划选择的唯一存储来源，不新增第二个相互竞争的 planner 设置。

新 ID 必须接通完整识别链：漫画侧 `isMangaPlanningPreset`、`mangaSegmentSchema`、`mangaOutputSchema`、`buildMangaPlanningContext`，SDT 侧 `isMangaContextPreset`、`getRequestEnhancedContext` 及各入口对规划 ID 的枚举分支。目前部分 Schema/画布逻辑只识别 narrative/v5 或 185 等旧值；仅新增 UI 选项会导致新模式缺少画布、套用旧主格描述，甚至落入普通插画分支。新路径的识别、布局描述和画布策略统一从 descriptor 派生，历史策略的行为保持。

推荐系统提示顺序：基础合同 → 当前任务范围 → 正文规划 → 格内绘图指导 → 资料使用规则 → 本入口交付要求。各模块只发一次；原 `contextAnalysisInstructions`、`segmentInstruction` 等在新路径中仅保留必要任务摘要，或由同一描述表派生，不能再追加另一套完整规划。

此顺序按任务裁剪：整段新建注入全文规划；单页新建使用受单页/格数限制的规划；已有页、单格和批量润色不注入“重新通读选材、决定页数”的全文规划，仅注入保留现有结构并执行明确修改的编辑策略。编辑仍复用基础和格内指导，不能一边发全文规划、一边靠最后一句“不要分页”抵消它。trace 同时记录所选组合及本次实际启用的任务策略。

正文、历史、角色卡、记忆、衣柜、画布、风格词仍通过 user/payload 作为数据输入。引用资料的优先关系由基础合同统一描述，SDT/Studio 不再分别追加可能漂移的身份、对白规则。

共享关系：漫画插件负责纯模块和漫画合同；SDT 负责收集当前请求资料及调用服务。Studio 通过现有 SDT API 收集所需资料，再调用同一个纯构建器。不要让基础构建器反过来修改 SDT 存储、发起网络请求或递归调用自己。

快照必须覆盖：解析后的组合 ID/版本、任务范围、画布、画风/语言/对白模式、所用角色资料和风格参考内容。发起请求后切换设置只影响下一次；不能在 await 返回后重新读取当前选择来解释旧响应。继续执行聊天切换、正文变更、记忆清空、卸载等失效保护。

`trace` 只记录模块 ID/版本或哈希、任务和组装来源，复用现有调试面板。最终绘图 prompt 不得包含 trace、规划说明或模块标题。正常成功请求仍只调用一次模型，不新增自动修复请求。

## 9. 风格预设与三个模块如何相处

第一阶段继续保留 `injectPresetsToTagger` 开关及外部预设的存储/最终绘图钩子。

新分层路径把启用的 `stylePreset` 作为独立资料对象传入，基础层只有一条稳定说明：参考其画风与视觉质感，不让资料改变任务边界、页格结构、角色事实和文字合同。不再把用户的整段 positive 拼成另一段系统命令，不再称漫画输出为普通 `scene`。

首版保持入口原有注入范围：SDT 正文、手动描述、单页测试在开关开启时参考外部风格；Studio 与已有页 AI 润色目前没有这项注入，新构建器不默认为它们增加。后者以工作台画风或原绘图快照为准。统一的是漫画三个职责模块，资料权限按入口明确传递；不能为了复用函数顺手将当前人物档案、风格或其他后置指令带入编辑。

在风格参考关闭时不发送它。开启或切换风格时，基础/规划/V23 的模块内容、Schema 和角色档案不能随之改写；生成的视觉词可以按参考变化。黑白模式的灰阶合同优先于资料中的彩色色相要求。

不能依靠“名为 V23”自动分类或删除用户内容。若用户把完整系统指令存在绘图预设 positive 中，需在说明中明确其会直接进整页生图词；不静默迁移、不用语义正则猜测并删段。新的 V23 格内模块放在漫画插件模块注册表，不放进 `_promptPresets` 的绘图词字段。

外部预设最终仍能影响出图；这条直接拼接路径本轮不重构。因此排查成图时必须查看最终 NAI payload，不能只看 Tagger 请求便认定所有风格冲突已经解决。

## 10. 各入口迁移矩阵

| 入口/函数 | 任务边界 | 新组装要求 |
| --- | --- | --- |
| SDT 自动/手动触发正文：`buildRequestPayload`、`callOpenAiCompatible` | 当前楼层完整正文，可多页 | 捕获组合后调用共享构建器；不再额外重复追加完整 enhancedContext 规则 |
| SDT `callCustomHttp` | 与正文入口同范围 | 仍通过现有 `mangaInstruction/outputSchema` 传递同一 bundle，保留对外字段合同 |
| SDT 手动描述生成入口 | 描述可包含连续事件，按其现有任务约束规划 | 复用 bundle；显式要求应画与页面范围，不从普通 minSegments 推出漫画页数 |
| `parseTaggerSegment` 测试生成 | 现有接口只接受一页 | 传明确单页 task，不能带入多页自由扩展；超容量要给出可处理的说明/错误，不静默丢内容 |
| `runSegmentAiRefinement` | 仅修改指定已有页 | 传编辑 task，保留完整最新绘图快照与用户修改；不重选整段正文，不重新套默认档案 |
| Studio 新正文分镜 | 现有单页、自动 1～5 格或明确格数 | 同模块、不同 task/schema 适配器；超容量保留 `capacity_note`，不擅自变成多页接口 |
| Studio 单格润色 | 只返回当前格 | 其他格仅供连续性参考，不复述、不新增页面；任务约束优先 |
| Studio 批量润色 | 保留现有格数与顺序 | 明确编辑约束，保留未要求改变的文字、人物与页面内容 |

JSON 和工具调用用同一合同来源，工具模式不再同时要求普通文本返回 JSON。自定义 HTTP 的字段载体不同，但任务、模块和输出语义一致。兼容响应解析中的原生工具结构，不借本次工作扩展 Studio 当前不支持的服务商或多页功能。

传输适配按当前实现保留：

- 正文主链路 OpenAI 兼容请求可用 JSON 或 `generate_draw_spec` 工具；工具选择与流式处理保持原样。
- SDT 手动描述、单页测试、已有页润色目前使用普通 JSON，不因全局 `toolCallMode` 打开就擅自切成工具请求。
- 主链路/手动/测试 custom HTTP 发送业务 payload；已有页润色的 custom HTTP 发送 `{messages}`。不得统一成一种未经兼容的外部请求体。
- Studio 当前走 `openaiBaseUrl/model`，经 `callStructuredCompletion` 使用 JSON 或 `generate_manga_storyboard`，还保留缺失该 API 时的 fetch fallback；不会因为 SDT provider 是 custom 就走 customUrl。
- 原生 Gemini 等主要是现有响应格式的兼容，不代表已经存在独立的原生请求入口。提示词重构不宣称扩大响应解析支持面。
- 已有消息包装、后处理、合并由传输层处理，留在纯 builder 外；哪个入口原先启用就保留，不隐式扩展到原先绕过它的已有页润色。

既有单页/单格编辑返回形状可以继续不同；适配器只包装响应外壳，不复制一套完整漫画规则。所有成功输出继续走现有归位/归属校验、外貌解析、编译与保存流程；编辑保持显式 `[]` 清空语义，不误走新响应的旧格式恢复。

## 11. 配置与历史迁移

推荐首版只新增一个 UI 规划选项“漫画 · 正文分层规划（试用）”，值例如 `v_manga_layered_v1`。旁边用短说明显示“格内绘图：V23 漫画适配”，首版固定绑定，不再增加一个必须配置的下拉框。

普通 SDT 系统预设仍用于普通插画；开启漫画时界面应明确其由漫画规范管理。漫画开启/关闭的保存和恢复逻辑继续保护用户原来的普通/自定义系统提示。

实现新旧组合的明确分支：

- 新 ID 走新基础 + 新规划 + 独立 V23 模块。
- 旧 ID 走历史组合，不在旧 v5 全文后再叠一份 V23。
- 历史 `buildMangaSystemPrompt` 需要保留兼容实现；不要抽空其内容后让旧 ID 悄悄变成另一种行为。可为新路径新增函数，旧入口由 wrapper 分派。
- 若后续要提供 v5 的分层版，另建经过审阅的“仅规划”模块和新组合 ID，不能在同名旧 ID 下偷换含义。
- 旧缓存、已编辑页树和工作台草稿不自动改写；新组合在重新解析时生效。仅重绘旧图保持其绘图快照。
- 未知 ID 按既有兼容规则处理并在调试说明实际选择，不静默激活试用功能。

首版不改任何已存默认或选择。通过实际质量评估后，可在下一版本仅对没有已存选择的新配置调整默认值；历史用户自行选择即可回退。

版本号由实施者根据届时 HEAD 递增，同时更新 `plugins.json` 的版本及 `main` 缓存 URL。不要照本文基线覆盖更高版本。

## 12. 实施顺序与每步交付物

### A. 建立模块清单与新组合

先按现有规则列出归属，处理重复或相互矛盾的规则，再编写基础、正文规划、V23 漫画适配三个独立模块和组合描述表。为每个模块写简短职责注释。完成新纯构建器及调试 trace，旧入口仍可用。

交付：新组合能生成一个职责清楚、无重复全文规则的完整请求，协议与现有编译器相容。

### B. 先接 SDT 正文主链路

接自动/手动触发正文的 JSON、工具和自定义 HTTP；统一正文、角色资料和画布快照；走完模拟响应→归位/校验→外貌→编译→NAI 字幕的闭环。

交付：正常成功只有一次请求，多页保留，旧模式不变，失败不写记忆/缓存。随后接手动描述、单页测试和已有页修改，逐入口明确任务边界。

### C. 接工作台现有任务

替换重复组装，复用同一模块与任务适配器。保留单页、1～5 格、单格/批量编辑的范围与取消、竞争请求保护。UI 只做名称、选项与简短解释，不新增多页编辑器或布局画布。

交付：工作台与 SDT 使用同版本公共模块，单格编辑不会突然触发全文分页。

### D. 验收、文档和可回退发布

执行有针对性的请求组装和完整回归；保存普通场景的实际模型对照记录。更新使用说明，解释新旧组合、普通 V23 与外部风格预设的区别。工程验收通过后可作为试用交付；未进行真实评估必须写明，不能宣布漫画质量已经改善。

## 14. 真实模型与成图质量怎样验证

工程测试只能证明指令发对、解析编译正确。真实模型评估另行执行，调用前确认可用配置与相应调用授权，不把用户此前的出错剧情作为测试样本。

建议预备 8 类中性正文：单一定格、双人问答、长对白、递接动作前后、时间/地点转场、明确画外声、无对白动作、需要分页的连续事件。每类准备人工标注的关键事件、说话者、顺序、状态及结尾，不规定唯一正确页数/格数。

对照规模建议：8 段 × 每段 3 次 × 改前/改后两组，共 48 次解析；这是评估预算建议，不是本次文档已执行的调用。固定模型、参数、资料、画风、画布，记录实际旧组合 ID与新组合 ID。不能用不同故事或不同模型直接声称新提示更优。

分别评估模型原始 JSON 和程序归位后的页树，记录原始误归属率、自动归位率、最终错误率，避免程序修复掩盖提示词问题。

硬问题包括：不能编译、漏关键事件或结尾、说话者/台词次数/先后错误、编造事件、互斥动作同格、超出编辑范围。每项单独记数。软评分对分页、格的作用、具体切分/阅读路径、镜头表达分别给 0/1/2 分，盲评并保留具体理由。页数、格数、耗时和 token 用作观察值，不作为越多越好的指标。

首轮小样本的实际目标是发现失败模式：结构与任务硬约束全部通过；关键事件覆盖、台词归属不能比基线退步；布局与格内动作评分有可解释改善。样本仍出现高影响错误时保留试用，不直接升为默认。不要用少量成功结果承诺稳定遵循率。

解析评估之后，再选择少量已核对的普通页做生图对照，查看格界、动作可读性、人物连续性、气泡与字的实际结果。最终 NAI payload 一并存档，用来区分规划、编译、外部预设和绘图模型各环节问题。没有图像对照不能宣称成图质量改善。

## 15. 暂不实施与后续升级条件

首版不改成固定页模板，不写自动角色猜测器，不新增对白账本，不增加自动模型修复，不实现精确气泡坐标、本地字形叠加、逐格区域生成、多页 Studio 或通用提示词插件重构。

三层在一次请求中属于清晰的提示职责分工，**不是程序已经锁定了中间分镜**。模型仍一次输出整个结果，无法仅凭模块拆分保证第三层从未改变规划。

只有真实评估证明一次请求仍频繁重排/漏项、且代价可以接受时，再考虑可选两次流程：第一次返回已确认的页格/人物/对白/状态计划；第二次只返回以页、格、人物 ID 定位的视觉字段补丁。程序白名单合并，拒绝补丁改变结构、正文事实或对白。第二次仍允许返回完整页树就等于又做一次规划，不解决边界问题。

如需精确格位和文字排版，需要单独的几何/渲染方案；这与提示词分层是不同任务，不能在本轮承诺解决。
