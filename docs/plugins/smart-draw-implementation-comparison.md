# Smart Draw Trigger：此前讨论与当前实现的差异说明

整理日期：2026 年 10 月 12 日。

核对对象：`RBQ-Draw-Plugins` 当前本地工作区，源码版本 `6.5.33`，已提交基线为 `6756db6`；另包含尚未提交、发布的两处输入保留修复。

本文用于核对现有实现、此前讨论的范围和实际验证情况。它不提供规避审核的实施步骤，也不把提示包装当作服务商的审核凭据。

## 1. 结论

当前实现与此前讨论在部分结构上相近，但不是同一份实现。

此前讨论的是升级已有独立子开关；另一模型实际新增了独立的 `experimental_preset` 预设。该预设已有将本次分析规则和任务资料放入工具说明的分支，已有子开关仍维持只承载业务 payload 的行为。

因此不能将当前状态描述成“已有开关已升级为完整上下文模式”，也不能把新预设与原版、v2 的行为混为一谈。

## 2. 术语与范围

| 名称 | 本文中的含义 |
| --- | --- |
| 分析规则 | 本次入口已经组装的系统指令，如分镜提取、角色参考、记忆使用和当前模式规则 |
| 业务 payload | 本次实际收集的输入包，包含该入口的核心内容和入选参考资料 |
| 工具 description | 工具用途及当前实现附加的说明内容 |
| 工具 parameters | 输出结果的真实 schema；不是输入资料的另一种名称 |
| 消息列表 messages | 本次临时 API 请求的消息数组；不是酒馆保存的聊天记录 |
| 完整上下文 | 这里指本次已组装的分析规则与 payload，不等于整个聊天历史或所有角色卡、世界书 |

各项资料仍受原功能开关及收集条件约束。没有收集到的角色卡、世界书、记忆或画风资料，不会仅因改变输入位置而自动增加。

系统提示自身也可能包含记忆摘要等资料，所以“规则”和“数据”是职责划分，当前代码并没有将所有资料严格归于同一个字段。

## 3. 此前讨论与当前实现对照

下表中的“此前讨论”是会话记录，不表示这些差异已被实现或已经验证。

| 对比项 | 此前讨论的方案 | 当前代码实际状态 |
| --- | --- | --- |
| 功能入口 | 升级现有“剧情与资料写入工具说明”子开关 | 新增独立 `experimental_preset` 预设；原子开关行为保留 |
| 规则与资料 | 本次分析规则和实际业务资料分区承载 | 新预设分支包含本次系统分析文本和任务数据，另带该预设的包装说明 |
| 消息布局 | 两条固定消息：system、user | 新预设定义了 system、user、assistant、user 的四条默认消息布局 |
| 原版与 v2 | 完整上下文能力由独立子开关控制 | 目前原版及 v2 没有因此变成新预设；原子开关仍只迁移业务 payload |
| 输出结构 | 保留按任务模式选择的真实工具 schema | 保留了普通插画、漫画、分层任务的 schema 分支，但部分字段说明和必填要求有调整 |
| 三入口 | 自动、手动、测试遵循同一传输选项 | 三个 OpenAI 兼容入口都接入了新预设分支；各自分析对象与任务限制仍不同 |
| 工作台 | 需要保留工作台自身的任务与输出契约 | 本地修复后，公共消息接口向工作台返回标准 system／user 消息，保留其自身输入与工具 |

“四条消息”描述的是新预设默认声明，不是所有设置组合都保证四条：后置提示开关会影响末尾消息，相同角色合并选项也需要按实际请求判断。消息条数本身不能证明请求保真或解析质量。

三个入口接入同类行为，也不等于消息组装只存在一份实现。当前自动、手动、测试各自保留新预设的消息分支；共用的是工具构建、部分响应处理，以及普通请求和 JSON 回退构建器。

## 4. 现有开关分别做什么

### 4.1 主开关 `toolCallMode`

它决定三个 OpenAI 兼容绘图入口通过工具参数还是 JSON 交付结果。它不决定哪些角色卡或世界书会被收集。

本地修复后，选中新预设但关闭 Tool Call 时，自动、手动、测试使用标准 JSON 请求，保留本次分析规则和完整已收集 payload。

### 4.2 子开关 `toolInputInDescription`

对应界面上的“剧情与资料写入工具说明”。它仍是原来的 payload 承载选项，默认关闭。

在适用的工具请求中，本次业务输入包被附加到工具说明，任务 user 消息改成固定读取说明；系统分析协议和其他消息仍按原流程处理。它没有被升级成迁移全部系统分析文本的选项。

### 4.3 独立预设 `experimental_preset`

完整分析文本与任务数据的封装属于这个新增预设的分支，不由原子开关单独定义。该分支优先于原 payload 子开关的封装分支。

因此两个设置不能视为同一个功能，也不能用“子开关开着”推断当前请求已采用新预设的完整封装。

## 5. 三个入口与漫画工作台的区别

| 入口 | 核心分析内容 | 输出契约 |
| --- | --- | --- |
| 自动楼层分析 | 当前楼层正文及该次入选参考资料 | 绘图分镜，保留楼层关联与锚点要求 |
| 手动描述生图 | 用户在手动功能中输入的描述 | 按手动任务生成分镜 |
| 测试解析 | 测试功能中的描述 | 保留测试任务及模式对应的数量限制 |
| 漫画工作台生成 | 工作台自己的画面描述 | 工作台的一页／画格结构 |
| 漫画工作台润色 | 已有分镜及用户的编辑要求 | 保留或按编辑要求调整现有结构 |

漫画工作台的画面描述、已有分镜不是酒馆当前楼层正文。它虽然复用智能生图的接口配置和公共消息函数，但有自己的分析规则、工具名称 `generate_manga_storyboard` 和输出 schema。

公共 `buildSdtMessages` 只返回 messages，不会自动将工作台资料送到另一工具。维护这个接口时，必须以调用者实际收到和发送的内容判断是否发生输入丢失。

## 6. 两处已确认问题与本地修复

### 6.1 工作台输入被公共消息接口丢弃

原提交中，公共接口在新预设状态下跳过调用者的分析规则和任务内容。工作台随后使用自己的工具，而该工具没有接收到被移出的资料，导致生成或润色缺少实际输入。

本地修复后，该公共接口在上述状态下返回调用者原有 system 规则和 user 内容两条标准消息。工作台继续发送自己的描述、已有分镜、画布及入选参考资料，工具和 schema 由工作台本身提供。

### 6.2 关闭 Tool Call 后缺少业务数据

原提交中，关闭 Tool Call 后仍会跳过正文和分析规则，但 JSON 请求不附带 tools，因而不存在其他承载这些内容的位置。

本地修复后，三个绘图入口在此组合下恢复普通 JSON 布局：system 保留分析规则，user 保留本次业务 JSON。保存的配置值没有被强制改写。

上述问题已使用中性输入复现，并用修复后的实际发包测试验证。修复没有证明新预设的所有组合都正确。

## 7. 输出 schema 与响应解析

保留真实 `parameters` schema 这一点与此前讨论相符，但“保留 schema”不等于“schema 完全没有改动”。新预设的普通插画分支修改了部分字段描述，并要求顶层 `shouldDraw`、`segments`；漫画和分层任务仍有自己的结构。

现有标准响应处理会独立累计多个工具调用，选择唯一匹配的函数，并对完整 JSON 对象、根必填字段和顶层类型做检查。拒绝、内容拦截和截断先于函数名称及参数错误处理。

这些检查不是完整 JSON Schema 验证器，也不代表所有嵌套分镜语义已经验证。

## 8. 验证记录与结论边界

当前本地工作区共 11 组模拟测试、420 项通过，语法和差异检查通过。相关新增覆盖包括：

- 普通插画、传统漫画、分层漫画的自动／手动／测试入口在关闭 Tool Call 时保留规则和任务 JSON。
- 工作台生成、已有分镜润色在 JSON／工具请求中保留自身输入和 schema。
- 公共接口保留字符串与对象输入，以及 Tool Call 开／关时不修改配置。
- 已有响应解析、拒绝与截断处理、角色记忆、漫画对白及插件生命周期回归。

这些测试没有调用真实模型或生图服务，也没有穷尽新预设启用工具调用时的全部任务模式、设置组合和实际渠道。

所以目前可以确认上述两个兼容问题已修复；不能把“420 项通过”写成“完整上下文封装和消息重组已经全面验证、零回归”。工具调用也不能被当作绕过服务商审核的保证。

## 9. 给接手者的准确状态描述

当前代码新增了一套独立预设，其中已有本次分析规则与任务数据封装，以及默认四条消息布局；现有 payload 子开关没有升级为同一功能。原版和 v2 的选择行为仍与新预设有区别。公共消息接口与关闭 Tool Call 的普通 JSON 路径已完成输入保留修复。

核对时应区分原已提交的 `6.5.33` 与当前本地未发布修复，并明确说明检查的是哪个入口、哪种模式、哪组配置和哪条请求。文档中的效果宣称、默认布局及历史测试数量，不能替代对应的实际验证。
