# 漫画模式第二轮检查：版式、文字归属与角色状态

检查基线：漫画模式 1.7.2、SDT 6.3.1，Git `da32152`。本轮检查及记录，不修改生产代码、提示词或用户设置。

后续处理：用户授权优化后，已实现 1.7.3 / SDT 6.3.2，详见 [实现与验证记录](rbq-manga-mode.md)。以下保留修复前的审计证据。第 3 项确认属于原版共有行为，未擅自更改序列化；第 10 项继续保持普通模式对已有档案的保护，使用已有手动提取入口补全。新增代码解决状态失效、同楼回写、外貌分类和配饰覆盖，恢复具体布局指令，并增加格数修正、文字归属诊断与全页已知颜色短语转换；不代表已通过真实出图质量评测。

证据：下载目录 `v1.1.json` 的实际内容与开关；`rbq_nai_20261004_021503.png` 的 PNG Comment 内嵌参数与原图；用户角色记忆截图；当前生产函数的本地复现。没有调用真实 Tagger 或绘图接口，没有将源图片内嵌参数等同于可获取的原始 Tagger JSON。

## 1. P1：通用版式要求弱化，最终布局停留在上下分段

位置：`plugins/manga-mode.js` 的 `GRAMMAR_PRESETS.cinema`、`buildMangaPlanningPrompt`、`buildMangaSystemPrompt`。

实际 PNG：832×1216，`use_coords=false`；布局为 `4 panels, vertical layout`，四个位置为 `top panel / middle-top panel / middle-bottom panel / bottom panel`。没有主格面积、左右相邻关系、纵长格或插入关系。画出的四条横格与这份请求一致。不是插件硬编码所有自动页为四格，也不能仅凭图片断定用户选择了经典四格。

原版 `panel_universal` 要求主格位置及大致面积、辅助格宽窄高低和相互排列、各格唯一位置称呼，包含“每个格子必须不同大小”；当前只保留概括性的主辅格和景别要求，前情末段也仅要求清晰主画面。示例侧重 top/bottom 标签，没有完整示范主辅格的面积和邻接关系。这会允许模型用最省事的纵向列表完成任务。

原文件保存配置同时启用 `panel_universal` 和 `panel_shounen`；后者要求半页以上主格与至少两格大角度斜切。插件为单选文法，不是同一组合。原版启用固定六页，SDT 自适应页数，两者容量预算也不同。这些是比较条件差异，不等于应该把所有剧情强制改成六页或斜切。

修复方向：保留简短一次请求，把主格大小、辅助格排列和阅读路径落实到最终页面与格内词，按剧情选择布局。不要随机轮换模板，不把经典四格合法的规整排列全局禁掉。长分析并非必要条件。

## 2. P1：实际生成参数中，可见人物对白放进了全局字段

实际 PNG 中“这几个人，今天晚上处理掉……”与“今晚回老宅吃饭吧……”仅在 `v4_prompt.caption.base_caption`，不在任何人物 `char_caption`；对应画面中两位说话人均可见。女方回答和末格“哼。”则在对应人物槽。首格对白被画成纸张上的内容，属于实际成图问题，不能仅看汉字是否清晰。

当前指令已经要求可见说话者的台词进人物槽，但本次输出没有落实。没有原始 Tagger JSON，不能进一步断言是 page.non_character、panel.non_character 还是 description 放错。编译器不会从人物槽移出对白，但会接受落在全局来源字段的对白。

原版 `nai5_syntax` 同样明确这项归属。修复方向是核对归属和增加可定位诊断，不是改变台词语种、删掉双语原句或无依据猜说话人。

## 3. 原版与当前共有的限制：非人物文字块合并

位置：`plugins/manga-mode.js:312` 的 `joinMangaCaptions` 与 `compileMangaPage`。

复现输入：P1 非人物字段写“右上小格、旁白、Text: 次日”，P2 写“底部大格、拟音、Text: 咚”。编译输出把全部视觉说明放在前面，末尾仅剩 `Text: 次日\n\n咚`。两段文字和各自画格、类型的边界没有作为对应块保留。

确定的是字段关联被扁平化；是否错位取决于绘图模型，不能声称每次必错。补查发现原文件 `extensions.tavern_helper.scripts` 内嵌完整“漫画台 v1.1”脚本：`parseV83ImageProtocol` 同样把全部视觉说明连接，再将各非人物文字用空行连接到一个末尾 `Text:`。此前“没有附原版脚本”的判断错误。这不是适配独有的回归，不能以“恢复原版”为由修改序列化。

如需改善，应作为独立实验，用真实旁白＋拟音、多格画外声验证；不要只改成更多 Text 标记就宣称解决。优先落实第 2 项原版已有的对白归属约束。

## 4. P1：同义写法未识别，状态替换和镜头裁切同时失效

位置：`normalizeMangaMemoryTags`、`mangaAppearanceTag`、`resolveMangaAppearances`。

用用户截图中的原词复现：

- `elegant updo style` 未识别为发型，设置 `state.hair_style="hair down"` 后同时保留盘发和散发。
- 手部特写仍自动加入 `elegant updo style, voluptuous body, red lipstick`；未知 base 标签被无条件保留到任何非空 visible 中。
- 上身镜头漏掉 `keyhole cutout`，腿部镜头漏掉 `side slit`；未知 outfit 标签却只在全部七个部位可见时保留。

这不是词有没有英文、是不是长自然语言的问题，而是分类器过窄，加上未知固定外貌与未知服装的处理相反。普通姓名与确切数值需要保留，不能用重新删除未知词作为修复。

## 5. P1：服装仍整组覆盖，正确配饰会被误删

位置：`mangaAppearanceTag` 的统一 `outfit` 组和 `resolveMangaAppearances` 的 `groups.has(info.group)`。

复现：记忆只有 `white shirt`；本格头面和上身可见，positive 为 `white shirt, glasses, necklace, holding book`。结果仅 `girl, blonde hair, white shirt, holding book`，眼镜和项链丢失。保存一件衬衫不代表所有配饰都已知，更不代表它们互斥。

修复方向：按衣物部件或确定冲突属性替换，区分已知完整换装、档案漏项和本格新增可靠细节。

## 6. P1：同楼重新解析，画面与记忆衣着分叉

位置：`plugins/smart-draw-trigger.js:6558` 的 `changedDuringRequest` 判定。

复现流程：

1. 初始 red dress；第 1 楼解析为 blue coat，并保存。
2. 对同一楼再次捕获真实请求上下文，读取到正确的楼前 red dress。
3. 新响应明确换成 green coat。
4. 当前画面为 green coat，但保存及下一楼参考仍为 blue coat。

原因：代码拿“请求的楼前服装”与“当前楼末服装”比较，把本来就不同的两个时间点误判为用户在请求期间手动换装。

修复方向：单独记录请求发起时当前档案版本/实际服装，用于并发保护；楼前状态只用于该楼绘图，不能兼任并发修改基准。

## 7. P1：改写后不再出图，旧剧情状态仍污染后续楼层

位置：`normalizeTaggerResult` 仅在 shouldDraw=true 时学习；`mangaStateHistory` 只按 messageId 保存。

复现：第 1 楼设为散发＋blue coat，之后修改正文并重解析为 `shouldDraw=false, segments=[]`。第 2 楼仍收到散发＋blue coat，旧楼状态没有失效。

静态检查还发现状态记录没有正文哈希或 swipe 身份，也没有删除楼层的清理逻辑。图卡缓存已按 mesHash 检查，但状态历史没有同样的版本校验。删除/切换分支问题属代码缺口，未在真实酒馆 UI 中操作复现。

修复方向：状态与消息版本绑定，正文改变、分支切换、删除和无图重解析都要有失效策略；不得凭空恢复为某套默认服装。

## 8. P2：黑白转换责任不一致，颜色处理覆盖不完整

位置：`buildMangaSystemPrompt`、`monochromeCharacterTag`、`enhanceMangaPayload`。

一段指令让资料保持原色并由程序转换；另一段要求所有绘图字段都转灰阶。原色记忆和灰阶绘图本可分工，但“由程序统一转换”的承诺超出实现：人物白名单仅识别部分发眼和衣物，base 不执行相同转换。

复现：`blonde hair` 转为 `light grey hair`，`red lipstick` 和 `red pen` 保留原样。实际 PNG 的首格文档及人物槽均有 red pen，图中笔及标记为红色。

实际参数还同时包含上游 `flat color / cell shading / anime screencap` 等画风及黑白词。存在方向竞争，但不能仅凭一张图把全部颜色问题归因于 Prompt Presets。本轮不修改该插件或拼接。

修复方向：明确持久资料与最终绘图表达的职责，补足已知颜色短语处理，正文与姓名不改；实际效果需要出图比较。

## 9. P2：结构通过不代表页数、人数、构图要求落实

位置：`compileMangaPage` 与模型提交核对。

复现：page.base 写 `comic, 4 panels`，panels 实际只有 1 格，当前编译成功并原样发送。主格面积、位置重复和人物归属也未形成可诊断的语义检查。实际 PNG 的基础提示中没有明确整页 1girl/2boys 等人数词；不能说当前程序会自动纠正。

修复方向：能从结构确定的信息本地生成/核对；不能可靠确定的给予警告。不要恢复逐句 source 账本、整轮模型重试，或因某个措辞不匹配导致整楼报错。

## 10. P2：首次漏项会固化，自动建档缺少可靠的补全路径

位置：SDT 的 `buildCharacterMemoryPromptModule` 与 `learnMangaCharacterMemory`。

非空 base 默认不更新，已有非空外貌档案也会跳过首次角色卡注入。这可防止漂移，但一份只保存头发、漏掉眼睛的档案，不能靠下一次普通生成自动修复。用户截图缺少此前的 brown eyes/side bangs/wide hips 是观察事实；没有本次角色卡与原始响应，不能判定这些特征此刻都应存在。

这项是现有策略的能力缺口，不是删除标签的证据。修复需要可靠来源支持的补缺流程，区分补漏和覆盖已有特征；不能由程序猜眼色。

## 工作台边界及非缺陷项

- 工作台自动解析硬限制单页 1～5 格，接口只返回 panels；自动 SDT 才支持多个 segments。长剧情工作台模式可能压缩或遗漏，这是功能边界，不能归因于 SDT 的三条横格。需要独立决定是否支持多页，不宜直接扩大本次改动。
- 工作台首次解析丢弃 visible 警告；单格与批量润色使用完整快照，避免旧档案覆盖，但新模型响应是否保留所有特征仍靠模型。这些入口的诊断一致性可继续补足。
- 图片旁重绘复用原分镜，换 seed 不会重新规划，这是设计行为。需要在界面上让它与重新解析正文的区别更明显。
- 3 格或 4 格本身合法；全宽横格也能服务剧情。问题是长期单一、没有主辅变化，而不是必须每页做不规则拼贴。
- 人物 center 全为 0.5 但 use_coords=false，不是本次四条横格的直接原因，不应直接强开手动坐标。
- PNG 中的 Unicode 和换行经正常 JSON 解码均为真实文本；本轮没有发现该图存在把字面量反斜杠 Unicode 当台词发送的问题。

## 验证与处理顺序

现有 72 项漫画回归、17 个情境场景的 289 项断言和 15 项提示词检查均通过，两份插件语法检查通过。新增本地复现覆盖上述分类、误删、文字扁平化、格数不符和两种状态回滚问题，旧测试未覆盖这些情形。因此上轮“九项均修复”仅覆盖既定复现，不代表完整机制或实际画质已验证。

建议顺序：先修确定性的状态回滚和特征误删；落实原版对白归属；恢复原版布局要求并核对最终页格词；最后按同一段正文真实重新解析比较版式、动作、对白和延迟。非人物文字合并属于原版共有行为，不列为恢复原版所需的修改。不能只靠重绘同一提示词评估前情/分镜改动。

原版完整流程补查见 [原版脚本与规划流程](rbq-manga-v1.1-runtime-review.md)。本轮仅更正审计文档，未修改生产代码。
