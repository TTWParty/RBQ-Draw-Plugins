# Smart Draw Trigger 的 LLM 输入与工具调用说明

核对日期：2026 年 10 月 12 日  
插件版本：6.5.33  
当前工作区基线：`RBQ-Draw-Plugins`，版本 `6.5.33`<br>
初次源码核对基线：`RBQ-Draw-Plugins`，提交 `ae4f47b`<br>
宿主仓库基线：`st-scene-trigger`，提交 `2dd38fc`

本文记录智能生图触发器实际传给 LLM 的内容、各功能开关如何影响输入、角色记忆如何建立与复用，以及工具调用的改进说明。已包含 v6.5.33 的三入口「剧情与资料写入工具说明」子开关升级：完整上下文分区迁移至工具说明，以及请求消息列表彻底重组为两条固定纯净消息（system、user）。

**核心结论：插件的自动分析对象是当前楼层正文，并结合前情、人物设定和已保存状态生成可定位的分镜。开启 Tool Call 后，自动、手动、测试三个 OpenAI 兼容入口均通过 `generate_draw_spec` 工具参数交付结果；开启「剧情与资料写入工具说明」子开关后，本次已组装的视觉分析规范（VISUAL_ANALYSIS_GUIDELINES）与业务任务数据包（Task Input JSON）统一分区写进该工具的 description，并将临时 API 请求消息彻底重组为固定 2 条纯净消息（Turn 1 为结构化工具引导 system，Turn 2 为读取指令 user），彻底剔除正文台词、敏感标签和破限多轮对话。关闭 Tool Call 时自动回退标准 JSON 布局，保留全部规则与数据。**

## 1 插件要完成的分析任务

自动楼层分析需要回答以下问题：

1. 当前楼层是否存在值得配图的视觉内容。
2. 应提取多少个独立分镜，各分镜对应什么时刻。
3. 每个分镜里有哪些人物、环境、衣着、动作、表情和构图。
4. 图片应插在正文什么位置。

普通插画结果以 `shouldDraw`、`segments`、`scene`、`characters` 等字段表达。`anchor.text` 按普通模式提示要求，从当前正文逐字摘取 10～40 字片段，供插图定位使用；不是复制整段正文，也不应取自历史消息。

漫画模式的 `segment` 通常对应一页图片，页内另含画格、人物、对白等结构。手动生图则以用户输入的画面描述为核心，其数量和触发要求可以不同，不能把所有入口等同于自动楼层扫描。

源码依据：`buildRequestPayload`、`getMangaOutputSchema` 及各手动请求入口。参见附录 A。

## 2 一个请求实际由哪些部分组成

概念上可以分成任务指令与业务素材，但使用工具调用时，实际请求还有独立的工具定义与生成参数。

| 请求部分 | 主要内容 | 职责 |
| --- | --- | --- |
| 系统及其他指令消息 | 生图规则、角色参考规则、增强分析指令、选用的包装预设 | 说明如何理解输入与组织结果 |
| 业务任务载荷 | 当前正文、前情、角色卡、世界书、记忆、分镜要求等 | 默认位于 user；新子开关生效时写入工具 description |
| 工具定义 `tools` | 函数名称、用途说明、`parameters` schema，以及子开关选入的本次输入 | 描述工具及结果结构，并在选用时承载任务输入 |
| 请求配置 | 模型、温度、流式设置、`tool_choice`、可选思考参数 | 控制接口行为 |

当前实现并非严格把“所有规则”放在 system、“所有数据”放在 user。比如 `segmentInstruction` 在 payload 中，角色记忆可能同时出现在系统提示与 payload 中，包装预设也可能生成多条 system、user、assistant 消息。

自动 OpenAI 兼容请求的基本流程为：

```text
读取本次设置与消息快照
  → 收集当前正文和参考资料
  → 组装 payload 与模式对应的系统指令
  → 按开关把业务输入放入 user 或工具说明，组装指令与后置提示
  → 设置工具定义或 JSON 输出模式
  → 发送请求并读取响应
  → 归一化分镜结果与处理角色记忆
  → 交给后续生图及卡片插入流程
```

这里的 `generate_draw_spec` 主要承担“提交分镜结果”的作用。模型返回工具参数后，插件解析并使用这些参数；仅出现工具调用并不意味着模型已经执行图像生成，也不表示接口的内容审核被关闭。

## 3 系统提示和规则层

### 3.1 基础生图规则

普通模式使用当前选择的生图提示词预设。主要职责包括分镜提取、场景与角色拆分、英文绘图标签、原文定位和输出格式约束。

“禁止质量词、只输出纯 Danbooru 标签”不是所有历史预设都统一遵守的总规则：部分预设允许自然语言补充空间关系，部分历史预设包含质量词。应以本次实际选中的预设为准。角色记忆规范里的角色 `base` 一般使用 `girl` 或 `boy`，而不是把场景人数标签 `1girl` 当作固定外貌。

### 3.2 前情增强与分镜规则

`enhancedContext` 会影响系统分析指令，也可能在 payload 中加入 `contextAnalysisInstructions`。普通模式的分镜要求还取决于显式图组标记、用户设置的最少分镜数等条件。

不同指令必须保持同一任务边界：历史消息用于理解状态与承接，当前楼层才是本轮插画分镜和原文锚点的来源。

### 3.3 角色卡参考规则

普通模式通常在开启 `injectCharacterCard` 且实际收集到角色卡信息时加入参考规则，要求以角色卡描述和入选内置词条作为人物设定依据。漫画模式有对应的参考规则，并按本次 payload 是否包含角色卡数据执行。

规则要求模型参考角色卡，不等于程序会发送角色卡的所有字段。字段范围见第 5 节。

### 3.4 角色记忆与衣橱规则

开启角色记忆后，系统提示可以包含当前聊天的已保存人物外貌、当前衣着、绘图身份和部分衣橱参考。普通模式还会在当前聊天无档案时，从已知全局角色资产中提供有限参考。

系统提示中的记忆摘要与 payload 中的 `characterMemory`、`characterWardrobes` 是不同位置的内容，目前可能重复。减少重复需要保留规则与数据的职责，不能仅按字段名删除一处后就假定行为不变。

### 3.5 编码与消息包装

启用 `lorebookBase64` 后，系统会附加设定解码指令，并将部分设定编码后发送。Base64 是可逆编码，不是加密，也不构成节省 token 或绕过过滤的保证。

`render_pipeline_v2` 会加入模拟守护进程身份、确认消息、固定审核结果文字和后置提示。所谓“防火墙”“关闭思考”在这些位置首先是提示文本；代码没有执行其中展示的终端审核命令。实际思考参数另由 `thinkingEffort` 等设置生成。

本文仅记录这些现有包装的结构，不把预设中的效果宣称视为已验证行为。

## 4 输入载荷字段清单

以下按字段家族列出当前自动请求和相关模式可能发送的内容。并非每次请求都包含所有字段。

| 字段 | 内容与用途 | 生效条件或注意事项 |
| --- | --- | --- |
| `mode` | 触发类型 | 自动请求取触发器类型；手动入口另行设置 |
| `marker` | 触发标记 | 无标记时可为空字符串 |
| `messageId` | 关联楼层 | 自动请求关联实际楼层；测试入口可使用特殊值 |
| `currentMessage` | 当前消息 `role`、`name`、`content` | 核心分析对象；正文优先取宿主消息，缺失时可回退 DOM 文本，并去掉首尾空白 |
| `recentMessages` | 最近消息的编号、角色、姓名和内容 | 按上下文设置读取；普通模式可能包含当前楼 |
| `contextCount` | 请求中记录的上下文数量设置 | 不是实际数组长度保证 |
| `minSegments` | 普通插画的最少或显式图组数量要求 | 特定分支才加入；漫画页数另行规划 |
| `segmentInstruction` | 当前任务的分镜规则 | 根据模式、图组、最少分镜和增强选项选择；分层漫画会移除并改用 bundle 指令 |
| `contextAnalysisInstructions` | 增强分析要求 | 取决于 `enhancedContext`；分层漫画会移除这一旧字段 |
| `lorebook` | 入选独立世界书条目 | 需要世界书总开关及来源、匹配、预算等条件通过 |
| `lorebook_base64` 和 `lorebook_encoding` | 世界书编码汇总与标识 | 编码开启时，可能与包含逐条编码字段的 `lorebook` 同时发送，并非二选一 |
| `characterCardInfo` | 符合条件的角色卡描述与内置条目 | 由 `injectCharacterCard`、角色范围、是否已有外貌档案共同决定 |
| `characterCardInfo_base64` 和编码标识 | 角色卡信息的编码形式 | 与明文角色卡载荷按该路径的编码开关选择 |
| `characterMemory` | 已保存角色身份、外貌、当前衣着等 | 记忆开启且有资料时加入；漫画可能使用按楼层还原的记忆参考 |
| `characterWardrobes` | 角色衣橱名、服装标签、触发词 | 记忆开启且有衣橱时加入 |
| `stylePreset` | 风格名、正面词和负面词 | 普通模式需开启 `injectPresetsToTagger` 且有有效当前预设；分层漫画使用自身快照 |
| `outputSchema` | 提示给模型的结果结构 | 普通模式多为字段说明对象；分层漫画可使用实际 schema；不等于整个工具定义 |
| `mangaCanvas`、`mangaInstruction` | 漫画画布和专用指令 | 根据漫画模式及 provider 加入 |
| `outputExample`、`mangaPromptTrace` | 分层漫画的结果示例和配置来源记录 | 分层漫画 bundle 注入 |
| `manualMode`、`manualInstruction` | 手动输入标记和要求 | 由手动或测试入口组装，不能按自动请求的固定条件推断 |

### 4.1 上下文数量的实际含义

宿主 `getRecentMessages(messageId, count)` 取的是截至当前楼层、包含当前楼层在内的最多 `count` 条消息，默认 5，代码限制范围为 1～50。

普通模式保留这份列表，因此当前正文可能既存在于 `currentMessage`，又存在于 `recentMessages` 的最后一项。漫画自动请求会过滤掉当前楼，因此默认通常最多留下前 4 条历史消息。文档或界面不应直接将这一设置解释为“前 5 楼”。

### 4.2 分镜指令的分支顺序

自动请求首先区分分层漫画、其他漫画与普通插画。普通插画内，优先按显式图组标记生成对应要求，其次考虑最少分镜设置，再考虑前情增强，最后使用一般自适应规则。

因此，`segmentInstruction` 不是每次都固定为同一段“全覆盖铁律”。读取最终请求快照，才能确认本次实际发送了哪一条要求。

### 4.3 敏感内容重试与特殊入口

`skipLorebook` 路径会同时跳过独立世界书和角色卡收集。开启相应重试选项后，重试请求可能与首发请求的资料范围不同，不能只凭界面开关推断最终请求内容。

独立手动、测试和公共 API 调用也有各自的组装入口。所谓“完整输入”应指本次实际构建后的请求，而不是把所有功能字段无条件合并。

## 5 角色卡注入与记忆生命周期

### 5.1 收集哪些角色卡

`collectCharacterCardInfo` 先检查 `injectCharacterCard`。关闭时直接返回空列表。

开启时，单聊只考虑当前角色卡；群聊考虑当前群成员卡。在部分宿主状态不完整时使用当前发言角色作为回退，不会扫描整个角色卡库。

每张符合条件的卡主要读取：

- `description`，可从兼容数据位置读取，保留其完整非空内容。
- `characterBookEntries`，只收集启用且无关键词或命中本次正文／历史的内置条目；入选条目的内容与条数当前不截断。

没有单独读取角色卡 `personality` 字段。性格若写在 `description` 或入选词条正文里，会随这些内容进入。

### 5.2 开启角色记忆时

关键跳过条件是：

```javascript
store.characterMemoryEnabled && String(profile?.baseTags || '').trim()
```

成立时，跳过该角色这条角色卡收集路径，包含其描述和内置世界书。这里检查的是有没有可用外貌档案，不是“第几次生图”。

典型生命周期如下：

1. 没有匹配的外貌档案时，收集符合条件的角色卡资料。
2. LLM 返回人物结构，程序处理可识别的角色名与可保存的外貌结果。
3. 普通模式在结果归一化和人物提示拼接阶段自动学习，不必等待图片生成成功。
4. 后续匹配到档案时，优先复用已保存的 `baseTags`，并继续处理当前衣着变化。
5. 用户仍可编辑、删除或重新提取档案；程序也可能修复绘图姓名。

首次请求没有可保存结果时，不能承诺当次建立完整档案；在请求前已经有匹配档案时，也可能直接跳过角色卡。漫画记忆另有按楼层和画格处理状态的机制，不应简化为只有一份永远不变的当前衣着。

准确的效果表述是“复用已保存的外貌标签，降低跨图漂移”。它不保证 LLM 永不出错，也不保证下游图像模型每次都画出完全一致的外貌。

### 5.3 关闭角色记忆时

不执行上述“已有 `baseTags` 就跳过”的判断，也不自动学习人物结果；已经存在的档案不会因此被删除。

在角色卡参考开关开启、候选角色和数据条件满足时，每次重新收集当前角色卡描述和本次入选的内置世界书条目。应称为“每次重新收集符合条件的资料”，不能称为“每次发送全角色卡全部字段”。

### 5.4 外貌和服装的区别

固定外貌 `base`、绘图身份 `name_tag`、当前衣着 `outfit`、当前动作 `action` 有不同职责。一般自动学习不覆盖已有固定外貌，服装可以随剧情变化；衣橱提供可复用服装参考。

模型输出中的不同姓名能否正确关联已有档案，也影响复用是否成功。相关验证应检查姓名关联与最终提交给生图模型的标签，而不只检查模型有没有在文字中承诺保持一致。

## 6 独立世界书的注入机制

SDT 的独立世界书路径读取自己的 `lorebookSources`。用户可以在插件界面选择绑定酒馆世界书或导入文件。不能笼统描述为自动继承酒馆里所有全局和聊天绑定的世界书。

候选资料必须先满足总开关开启、来源启用和词条未禁用。之后还受到以下规则影响：

- 主关键词与次关键词逻辑。
- 仅当前楼层设置和扫描深度。
- 常驻、粘性、冷却与概率。
- 互斥分组和优先级。
- 最多两轮递归激活。
- 总字符预算，默认 8000 字符；超过剩余预算的条目整条跳过。

因此，“正文关键词命中”既不保证条目最终发送，也不是所有入选条目的唯一来源。

这条路径不检查角色是否已有 `baseTags`，与角色卡参考路径相互独立。同一内容若既存在于角色卡内置书，又作为独立来源绑定，就可能在角色建档后仍通过独立路径发送。

## 7 当前 Tool Call 的实际行为

### 7.1 工具开关控制什么

自动、手动和测试三个 OpenAI 兼容请求开启 `toolCallMode` 后，代码发送 `generate_draw_spec` 工具定义，并首次强指定该工具，使用流式响应。关闭后，请求 `response_format: {type: "json_object"}`，保留原来的非流式 JSON 路径。

“JSON 模式”主要约束返回可解析 JSON；“工具调用”规定模型用工具参数交付结果；“严格 schema”进一步约束字段与类型。三者相关，但并不等同。

当前普通插画工具 schema 没有声明 `strict: true`，也未系统设置 `additionalProperties: false`。默认顶层只要求 `shouldDraw`；部分预设和漫画分支会额外要求 `segments`。本轮新增的本地检查只覆盖完整 JSON 对象、根 schema 的必填字段及已声明的顶层类型，因此打开 Tool Call 不能被描述为已经完成严格 schema 校验。

### 7.2 三个生图入口已统一传输选择

| 入口 | 当前请求行为 | 实际影响 |
| --- | --- | --- |
| 自动楼层 OpenAI 兼容分析 | 按开关选择工具或 JSON 模式 | 分析实际楼层及按设置收集的参考资料 |
| 手动输入生图的 OpenAI 兼容分支 | 按同一开关选择工具或 JSON 模式 | 使用手动描述及该入口选中的参考资料，保留多分镜生成流程 |
| 测试生图的 OpenAI 兼容分支 | 按同一开关选择工具或 JSON 模式 | 使用测试描述，仍按测试任务的数量限制输出 |
| 自定义 HTTP 分析 | 直接发送业务 payload | 不由这条路径自动封装 OpenAI `tools`；取决于自定义服务契约 |
| 公共 `buildSdtMessages` | 只构建消息 | 不负责添加工具定义或发请求 |
| 公共 `callStructuredCompletion` | 开关开启且调用方提供 tool 时使用工具 | 是否提供正确工具仍由调用方决定 |

手动和测试工具请求通过新增的 `callDrawSpecCompletion` 复用 `callStructuredCompletion`，再交给原有分镜归一化流程。普通插画使用普通工具 schema，漫画使用对应模式的工具 schema；分层漫画的工具定义与本次任务的 `outputSchema` 一致。`parseWithTagger` 和 `generateWithTagger` 经过测试解析入口，因此也遵守该开关。

传输一致不表示业务输入相同。自动楼层扫描、手动描述和测试描述仍保留自己的资料收集条件、数量限制和触发规则。

#### 本轮：共用常规请求构建器

`buildStandardDrawRequest(systemPrompt, payload, store, promptBundle)` 对普通 OpenAI 兼容请求返回相同的消息布局：

| 请求位置 | 保留的内容 |
| --- | --- |
| `messages[0]`，system | 本次已组装的分析规则，包括实际生效的角色参考、记忆和模式指令 |
| `messages[1]`，user | 本次业务 payload 的 JSON，包含该入口实际收集的正文和参考资料 |
| `tools[].function.parameters` | 普通插画、漫画或分层任务对应的真实结果 schema；Tool Call 关闭时不附工具 |

该构建器在 provider 非 `custom`，且 `geminiJailbreak`、`postProcessEnabled`、`toolInputInDescription` 均未开启时使用。自动、手动和测试入口共享这一构建步骤；Tool Call 开关继续决定工具参数或 JSON 输出。

开启上述任一兼容选项时保留既有分支。这次重构不改变资料收集，不把分析规则迁入工具 description，也不修改酒馆保存的聊天消息。工具调用仍受服务商的请求校验与内容审核约束。

### 7.3 输入位置与输出方式是两件事

v6.5.31 新增设置 **“剧情与资料写入工具说明”** 对应 `toolInputInDescription`，当前位于“提示词与破限 → 通信与结构化输出”中“结构化工具调用 (Tool Call)”开关下方，默认关闭。启用主 Tool Call 后可操作，点击保存后生效。

| 接口与开关 | 实际输入位置 | 输出方式 |
| --- | --- | --- |
| OpenAI 兼容，Tool Call 关闭 | 原来的 user 任务载荷；子开关禁用但保留选择 | JSON 模式 |
| OpenAI 兼容，Tool Call 开启，子开关关闭 | 原来的 user 任务载荷 | `generate_draw_spec` 工具参数 |
| OpenAI 兼容，两开关开启 | 本次完整 payload 追加到工具 description；user 使用固定读取指令 | `generate_draw_spec` 工具参数 |
| 自定义 HTTP | 原业务 payload 协议；新子开关隐藏且不生效 | 按服务端契约 |

子开关生效时，工具说明末尾的 `[Task Input JSON]` 标记之后是本次已组装的 payload JSON。正文、前情、分镜提取指令、世界书、角色卡、记忆、衣橱、画风和模式信息，只要本次实际包含，就原样迁入；原本未收集的字段不会因此增加。中文、换行、引号与反斜线通过 JSON 序列化保留，不改写正文。

user 任务消息固定为：“请读取 generate_draw_spec 工具说明中的本次任务输入，按系统规则分析并通过该工具提交结果。”普通插画、漫画及分层任务仍使用各自真实的 `parameters` schema。工具按请求复制，后续请求不会继承上一次的剧情或参考资料。

系统分析协议、选用的系统预设和后置指令仍在原消息层。原有系统模块也可能包含角色档案与画风资料，因此该功能迁移的是业务 payload，不表示全部人物资料只存在于工具 description。它不调整资料收集开关或角色卡建档生命周期。

此子开关在三个入口中优先于原 user 渲染包装：payload 直接序列化到工具说明，固定 user 指令不再套用 render／v2 的业务包装；系统预设及后置消息继续按原设置组装。它没有升级为“完整分析上下文写入工具说明”，本轮也未改变这一既有行为。公共 `buildSdtMessages` 和调用方自行提供工具的 `callStructuredCompletion` 不会自动迁移输入。

此前对照的 `linux_1.2.json` 内嵌脚本会重新组织 messages，把预设和历史资料放进新增工具描述，再从字符串工具参数还原正文。它与 SDT 的结构化分镜协议不同，不能把两者的 Tool Call 当作同一套实现。

“把剧情加入工具说明”改变输入存放位置；“开启工具调用”改变模型交付结果的形式；“启用严格 schema”改变服务端对输出结构的约束。这三项应该分别理解和验证。

### 7.4 已确认的输入保真问题

`wrapPayloadInRenderTelemetryV2` 接收对象时只替换 `segmentInstruction` 中的特定词组，接收字符串时会替换整个字符串。`buildSdtMessages` 会先把对象序列化为字符串，因此通过该入口时，正文和其他字段也可能被改写。

本地良性样例验证：正文“他们在车站牵手拥抱，然后挥手告别。”在字符串路径中被替换成“他们在车站人物多角色构图、然后挥手告别。”。这会造成模型看到的正文与真实楼层不同，增加原文锚点匹配失败的风险。该检查只运行纯函数，没有调用外部模型。

### 7.5 已确认的响应与错误处理边界

- 普通工具定义较宽松，`validateStructuredResult` 当前本身只是返回输入；工具参数现在另有根结构检查，其他归一化和漫画专用逻辑也有检查，不能据此说整个插件毫无验证。
- 普通归一化会在 `shouldDraw: false` 但仍存在有效画面数据时重新判为可生图，需要明确业务上是否接受这种恢复策略。
- SSE 参数按调用 `index`／`id` 分别累计，保留实际函数名；返回多个调用时选择唯一匹配的预期工具，不把其他工具参数拼入结果。只有一个无名调用时兼容接受；没有匹配工具或同名工具被调用多次时，分别报告非预期工具或无法唯一选择。
- 工具参数字符串必须通过 `JSON.parse` 并得到完整对象；原生对象参数也必须是对象，不能是 `null` 或数组。随后检查根 schema 的 `type`、`required` 和已声明顶层字段的 `type`。不自动修补损坏工具 JSON，也不剥除参数外的 Markdown 包装；普通文本 JSON 模式仍保留原有容错解析。
- 根结构检查没有覆盖嵌套 schema、枚举、额外字段或全部 JSON Schema 关键字，分镜语义与漫画规则仍由后续模式逻辑检查。完整对象检查也不等于已经实现所有异常 EOF 的传输完整性检查。
- 手动和测试的工具请求复用 SSE 解析，自动与共享请求在检查工具名称及参数前先处理拒绝、内容拦截与 `length`／`MAX_TOKENS` 截断，错误码保持一致。兼容端点忽略流式选项并返回完整现代、旧式或 Gemini 原生工具响应时，也按实际函数名选择结果。
- 自动和共享解析器收到 HTTP 200 的完整错误对象时保留服务端错误，不再将上游错误误报为缺少工具参数。
- 工具请求遇到 HTTP 400 或 500 会尝试 `auto`，失败后统一提示“不支持工具调用”；这不足以区分格式错误、服务故障、限制响应和真正的能力缺失。

这些是当前源码审阅发现，不代表所有模型或中转渠道都会触发相同问题。

自动与共享工具请求的主要错误码如下，原始输出随诊断保留：

| 错误码 | 含义 |
| --- | --- |
| `SDT_TOOL_RESPONSE_UNEXPECTED_FUNCTION` | 返回的具名工具没有匹配本次预期工具 |
| `SDT_TOOL_RESPONSE_AMBIGUOUS_FUNCTION` | 不能唯一选择工具，例如同名工具返回多次 |
| `SDT_TOOL_RESPONSE_INVALID_ARGUMENTS` | 参数不是完整的 JSON 对象 |
| `SDT_TOOL_RESPONSE_SCHEMA_MISMATCH` | 根类型、必填字段或已声明顶层字段类型不符 |
| `SDT_TOOL_RESPONSE_BLOCKED` | 服务商或模型明确拒绝／拦截响应 |
| `SDT_TOOL_RESPONSE_TRUNCATED` | 响应被输出长度限制截断 |

## 8 工具调用的推荐用法

本节为后续设计建议。三入口传输选择、常规请求构建和可选输入位置已按第 7.2、7.3 节完成，其余建议需要分别实施与验证；推荐目标是提高结构正确率、原文定位成功率和不同入口的一致性。

### 8.1 保持工具定义稳定

默认继续把当前正文与动态参考资料放在 user 任务载荷中；新子开关为可选的工具说明承载方式。两种方式都将输出结构保留在真正的工具 schema 中。

官方文档将函数 description 用于说明工具的用途和使用方式，工具定义也会消耗上下文与输入 token。将整包动态正文移入 description 没有天然的 token 节省，也没有已验证的分镜质量优势。根据缓存对稳定请求前缀和工具定义的要求，动态改写工具描述还可能降低缓存复用；这是对 SDT 的工程推断，实际影响需要测量。[O1][O3]

因此，不建议把“全部内容放进工具说明”设为默认最优方案。是否改变输入位置，应由解析率、锚点准确率、耗时和 token 的对照结果决定，不能仅凭预设名称判断。

### 8.2 用一个明确的工具提交最终结果

对一次普通分镜分析，目标是提交一次完整结果，而不是让模型自行决定调用任意工具。在支持的渠道上指定 `generate_draw_spec`，并根据供应商协议关闭不需要的并行工具调用。

强制调用结果工具不等于强制画图。正常的“不需要配图”也可以通过同一个工具返回，例如：

```json
{
  "shouldDraw": false,
  "reason": "当前消息没有新的可视化场景",
  "segments": []
}
```

`reason` 应记录简短、可核对的决定依据，不要求模型返回内部逐步思维过程。自动判断与手动强制生图应分别定义业务规则，避免通用包装直接覆盖触发判断。[O1][G1]

### 8.3 为支持的渠道使用严格 schema

对明确支持严格函数参数的渠道，使用与该接口兼容的严格模式。OpenAI 文档要求严格模式中的对象设置 `additionalProperties: false`，并将其 properties 字段列入 required；需要表达可缺省信息时，可按支持范围设计为 nullable 或采用统一空值约定。[O1][O2]

普通插画可统一要求 `shouldDraw`、简短 `reason` 和 `segments`；拒绝多余字段、错误类型和缺失的必要结构。空镜可允许 `characters: []`，不能为了满足结构而强造人物。

严格 schema 只能保证支持范围内的结构，不保证分镜合理、角色识别正确或锚点来自原文。复杂业务条件应在本地校验，不应假定所有供应商都支持完整 JSON Schema 特性。

### 8.4 保留本地业务校验

建议在交付生图前检查：

1. 收到的是预期工具，且恰好获得一份完整结果。
2. JSON 可解析，符合本次插画或漫画模式 schema。
3. `shouldDraw: false` 与空分镜一致；矛盾结果进入明确的错误或修复路径。
4. 普通插画每个 `anchor.text` 都能在请求时的当前正文中找到；找不到时不伪造定位。
5. 角色关联名能与记忆匹配，固定外貌与临时衣着没有混淆。
6. 漫画页、画格、对白归属及容量规则通过模式专用检查。
7. 用户切换聊天、删除或编辑楼层后，旧响应不会写回错误位置。

这些检查应在写入角色记忆和触发生图之前完成。当前某些学习动作发生在结果归一化内部，改造时需要将可产生状态变化的动作与纯解析、校验区分开。

若设置一次有限修复请求，应只提供具体校验错误和必要上下文，限制次数，并记录额外耗时。无法恢复时保留可理解的错误，而不是静默把不完整内容交给生图。

### 8.5 将流式响应作为传输选项

Tool Call 本身不要求所有供应商都必须流式。SDT 当前强制流式主要体现现有渠道兼容策略，应按已验证的端点能力配置，而不是当作普遍 API 定律。[O1][G1]

流式工具参数在接收过程中往往不是完整 JSON。需要按调用标识或索引分别积累参数，完整结束后解析；同时检查结束原因、截断、拒绝或供应商错误。中途断流不应因为局部文本看似可解析就直接作为成功结果提交。[O1][O2]

### 8.6 统一入口并区分供应商能力

自动、手动、测试现已共享工具选择开关与工具 schema 来源，常规请求共用两条消息构建器，手动和测试复用公共工具响应解析。兼容分支的请求构建、能力协商和错误分类仍可继续收敛。每个入口保留自己的业务 payload 和模式规则。

建议把以下能力按端点与模型分别记录：工具调用、强指定工具、严格 schema、JSON schema 输出、流式响应、并行调用控制以及思考参数。OpenAI 兼容协议、Gemini 原生协议和中转实现不能仅按模型名字推断完全一致。[O1][G1]

若仅为结构化抽取，也可在支持的接口上评估严格 JSON schema 输出作为替代。继续沿用工具调用能减少当前改动，但不应把工具调用视为唯一可靠的结构化输出方式。[O2]

### 8.7 根据实际错误进行有限降级

仅当错误证据表明某参数或能力不被支持时，才尝试相应降级。网络故障、限流、服务端异常、结构错误和限制响应应分别处理。

降级要记录首次请求方式、触发原因和最终采用的协议。工具模式降级为 JSON 时，要同步调整输出指令，避免请求未携带工具却仍要求调用工具。保留取消信号、超时与重试上限，避免无界重试。

### 8.8 用可观测数据选择最佳配置

为每次分析记录不含 API Key 的请求摘要：入口、模式、启用资料类别、实际协议、schema 版本、输入长度、入选世界书数量、结果状态、耗时和供应商返回的 usage。

排错时重点观察“实际发送了什么”，而不是只看设置面板上勾选了什么。完整正文和角色卡只在用户主动调试时查看；普通日志优先使用长度、计数和本地摘要标识。

### 9.1 推荐优先级

### 9.2 回归场景

使用普通、非露骨剧情即可验证工程正确性：单一场景、纯抽象闲聊、多阶段动作、两人换装、无人物空镜、角色首次建档、已有档案、内置世界书关键词命中与未命中、独立世界书超预算、漫画多页、手动输入、测试输入，以及请求期间切换聊天。

响应层另外覆盖：工具名错误、同时返回多个工具、缺失字段、额外字段、`shouldDraw` 与分镜矛盾、找不到原文锚点、SSE 分片拆在 Unicode 或 JSON 转义边界、中途断流、取消请求、401、429、500 和供应商拒绝／截断状态。

### 9.3 对照实验

以当前工具模式为基线，分别评估严格工具 schema、严格 JSON schema 输出和提示内容精简。每次只改一个变量，使用同一批固定素材与相同模型配置；非确定性模型应重复运行多次。

建议统计：

- 首次结构有效率与最终有效率。
- 原文锚点命中率。
- 分镜遗漏和多余分镜的人工评分。
- 人物关联及固定外貌复用准确率。
- 首次响应、完整响应的中位数及高分位耗时。
- 输入／输出 token、缓存 token 与重试次数。
- 不同入口和不同渠道的失败分类。

文档中的改进建议尚未进行真实模型对照，不能提前给出哪种配置成功率更高的数字。
